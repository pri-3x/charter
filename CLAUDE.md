# CLAUDE.md — Charter

Charter is a runtime authorization and audit layer for AI agents: a **policy gate** that sits
between an agent and the tools it calls, fused with a **tamper-evident audit ledger**.
Core invariant: **no verdict is ever returned before its ledger entry is durably committed.**

Read before coding, in this order:
1. `docs/DECISIONS.md` — resolved architectural decisions. Do NOT re-litigate these.
2. `docs/SPEC.md` — full system behavior: policy semantics, ledger construction, approvals.
3. `docs/API.md` — exact HTTP contract.
4. `db/schema.sql` — the database schema. Apply as-is; change only via a new migration file.
5. `docs/MILESTONES.md` — build order M1→M5. Work strictly in milestone order.
6. `docs/TEST_PLAN.md` — S1–S20, T1–T6, A1–A4. These are the acceptance criteria; a milestone
   is done only when its listed scenarios pass.

## Stack (fixed)
- Node.js 22, TypeScript (strict), ESM.
- HTTP: Fastify. Validation: zod. Logging: pino.
- DB: PostgreSQL 16 via `pg` (node-postgres). Raw SQL only — no ORM. Migrations are numbered
  SQL files in `db/migrations/` applied by a tiny runner script.
- IDs: ULID (`ulid` package). Hashing: node:crypto SHA-256. Signing: node:crypto Ed25519.
- Canonical JSON: RFC 8785 (JCS). Implement in `packages/shared/src/jcs.ts` with tests — do not
  hand-wave this; it is the correctness-critical component (see DECISIONS D3).
- Approvals channel: Telegram via `grammy` (long polling; no webhook needed for POC).
- Tests: vitest. Integration tests run against a real Postgres (docker compose).
- Demo agent: Anthropic API tool-use loop (`@anthropic-ai/sdk`), model `claude-sonnet-4-6`.

## Monorepo layout (npm workspaces — create it)
```
packages/
  shared/      # jcs canonicalization, hashing, types shared by gate+verifier? NO — see note
  gate/        # Fastify service: check endpoint, policy engine, ledger writer, checkpoint worker
  sdk/         # TypeScript client: CharterClient, guard() wrapper
  approvals/   # Telegram bot: context packets, approve/reject, hold resolution
  verifier/    # standalone CLI — MUST NOT import from gate/ or shared/ (see DECISIONS D6)
  demo-agent/  # customer-support agent with 4 tools, drives the test scenarios
db/
  schema.sql migrations/
policies/
  example.acme.yaml
```
Note on `shared/`: gate and sdk may share code. The **verifier re-implements** JCS + hashing
independently on purpose — duplication there is a feature, not a bug.

## Commands (set these up in root package.json)
- `npm run dev` — gate + approvals with tsx watch
- `npm run db:up` / `db:migrate` / `db:reset` — docker compose Postgres + migration runner
- `npm test` — unit tests; `npm run test:integration` — scenario suite S1–S20
- `npm run tamper-demo` — scripted T1/T3 tamper test with verifier output
- `npm run demo` — end-to-end 5-minute demo script

## Conventions
- Fail closed everywhere: DB down, policy missing, unknown tool, unknown agent, timeout → the
  action does NOT proceed. Never default-allow. If you find yourself writing a fallback that
  allows, stop.
- Ledger tables are INSERT-only. The app connects with the `charter_gate` role which has no
  UPDATE/DELETE on `ledger_entries`/`checkpoints` (see schema.sql). Never work around this.
- The verdict + ledger insert happen in one Postgres transaction. Return the verdict only after
  COMMIT succeeds.
- All money amounts are integers in minor units (paise). Currency code alongside. Never floats.
- Timestamps: ISO 8601 UTC with milliseconds, generated by Postgres (`now()`), not by app code.
- Env config via `.env` (see `env.example`). No secrets in code or logs. Never log full action
  parameters at info level (they may be sensitive) — log the params hash.
- Every HTTP handler validates input with zod before touching business logic.
- Keep functions small; write unit tests alongside (`*.test.ts`).

## Definition of done per milestone
Milestone tasks are in docs/MILESTONES.md. Done =
(1) listed scenarios in TEST_PLAN pass in CI-style run,
(2) `npm run demo` still works end-to-end,
(3) no TypeScript errors with strict mode, and
(4) a short PROGRESS.md entry describing what was built and any deviations (deviations from
    DECISIONS.md require an explicit note and reason).

## Integration tests need a clean chain
`npm run test:integration` runs `db:reset` first, deliberately. The ledger tables are INSERT-only, so
tests cannot clean up after themselves, and two scenarios change tenant-wide state on purpose: **S14**
activates a policy that caps `support-agent` to ESCALATE and **S17** activates further versions. Run
against an accumulated chain, later runs then see ESCALATE where they expect ALLOW. Use
`npm run test:integration:only` to run the suite against a database you have already prepared.
